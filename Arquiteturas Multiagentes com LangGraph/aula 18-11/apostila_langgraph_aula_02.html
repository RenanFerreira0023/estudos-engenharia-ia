1. O que faz um agente ser autônomo

Vídeo · 08:35–13:55

Na Aula 1 você viu a chain (passos fixos) e o router (o modelo escolhe uma rota). Agora o foco é autonomia. O professor parte da definição do livro Artificial Intelligence: A Modern Approach (Russell e Norvig): agente é algo que age. Para isso, ele precisa de três coisas:

RequisitoO que significa
Capacidade de decisãoEscolher o que fazer diante de um objetivo.
Acesso a múltiplas opçõesSem alternativas não existe decisão. O agente precisa de um catálogo de ações (ferramentas).
Interação com o ambientePerceber ou mudar algo fora do modelo: APIs, bancos, buscas, calculadoras.

O que separa o agente moderno das arquiteturas anteriores é o laço controlado pela LLM. O modelo não só toma uma decisão prevista: ele também define quais decisões tomar e quando parar. No grafo, esse laço fica visível.

Roteiro da aula: ReAct, First Model (otimizar latência), pré-seleção dinâmica de ferramentas, Reflection e Plan-and-Execute.

2. ReAct: do prompt em texto ao tool calling nativo

Vídeo · 13:55–20:45

ReAct vem de Reasoning + Acting (raciocínio e ação). Ele junta dois mecanismos:

  • Chain of Thought: quebrar um problema em etapas intermediárias de raciocínio.
  • Tool calling: o modelo pede a execução de funções externas.

Como era antes (GPT-3.5 turbo)

O desenvolvedor descrevia as ferramentas em texto no prompt e exigia uma saída em CSV, por exemplo search,30th president of the United States. A temperatura ficava baixa, porque não se quer criatividade na chamada de ferramentas. O código interceptava essa string, executava a busca e colava o resultado no prompt para uma nova chamada. Isso se repetia até o modelo emitir a resposta final.

Como é hoje (desde o GPT-4o)

Os modelos atuais passaram por fine-tuning para chamar ferramentas de forma estruturada. Não é mais preciso pedir CSV:

  • Os schemas JSON das ferramentas são ligados ao modelo com .bind_tools(tools).
  • Quando decide agir, o modelo devolve uma AIMessage com a propriedade tool_calls: name, args (dicionário) e um id de rastreio.

O LangGraph orquestra o laço com dois componentes prontos de langgraph.prebuilt:

ComponenteO que faz
ToolNodeNó especializado. Lê a última AIMessage do estado, executa as ferramentas pedidas (em paralelo, se houver mais de uma), captura erros e os transforma em mensagens que a LLM entende para se corrigir. Devolve ToolMessage ligadas a cada tool_call_id.
tools_conditionFunção de roteamento condicional. Se a última AIMessage tem tool_calls, manda para o nó "tools". Se não tem (o modelo respondeu em texto), manda para END.

3. Montando o ReAct no LangGraph

Vídeo · 20:45–27:15

3.1 · As ferramentas

O professor cria duas ferramentas. A calculator recebe uma expressão em texto e a calcula de forma segura. A busca usa a Wikipedia no lugar do DuckDuckGo do livro, porque o DuckDuckGo dá muitos problemas no Colab.

20:53–23:24 · Trecho do notebook do professor (Aula 2.ipynb, célula de ferramentas); imports omitidos
@tool
def calculator(expression: str) -> str:
    """Calculadora matemática segura para expressões aritméticas.

    Use esta ferramenta sempre que precisar calcular somas, subtrações, multiplicações,
    divisões ou potências exatas.

    Args:
        expression: Expressão matemática válida em sintaxe Python (ex: '1933 - 1872').
    """
    allowed_operators = {
        ast.Add: operator.add, ast.Sub: operator.sub, ast.Mult: operator.mul,
        ast.Div: operator.truediv, ast.Pow: operator.pow, ast.USub: operator.neg,
    }

    def _eval(node):
        if isinstance(node, ast.Constant):
            return node.value
        elif isinstance(node, ast.BinOp):
            return allowed_operators[type(node.op)](_eval(node.left), _eval(node.right))
        elif isinstance(node, ast.UnaryOp):
            return allowed_operators[type(node.op)](_eval(node.operand))
        else:
            raise ValueError(f"Operação não suportada: {ast.dump(node)}")

    parsed = ast.parse(expression.strip(), mode="eval")
    return str(_eval(parsed.body))

# Trocando DuckDuckGo pela Wikipedia (muito mais estável no Colab)
api_wrapper = WikipediaAPIWrapper(top_k_results=2, doc_content_chars_max=1500)
search = WikipediaQueryRun(api_wrapper=api_wrapper)

tools = [search, calculator]

@tool transforma a função em ferramenta: o nome, os tipos dos parâmetros e a docstring viram o schema que o modelo lê. _eval percorre a árvore da expressão (ast.parse) e só aceita os operadores do dicionário. Qualquer outra coisa gera erro. WikipediaAPIWrapper busca o termo e devolve os 2 primeiros resultados (top_k_results=2), com até 1500 caracteres. WikipediaQueryRun é a ferramenta que o agente chama, com o nome wikipedia. As classes vêm do langchain-community, por isso aparece um aviso de depreciação.

3.2 · Modelo, estado e nó de raciocínio

23:43–25:02 · Trecho do notebook do professor; comentários de numeração omitidos
model = ChatOpenAI(model="gpt-4o-mini", temperature=0.1).bind_tools(tools)

class ReActState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]

def model_node(state: ReActState) -> dict:
    res = model.invoke(state["messages"])
    return {"messages": [res]}

O modelo é o gpt-4o-mini com temperatura baixa (0.1) e já recebe as ferramentas com bind_tools. O estado ReActState tem só messages, com o reducer add_messages que você viu na Aula 1. O nó model_node envia todo o histórico ao modelo e devolve a nova mensagem: ou uma resposta em texto, ou uma AIMessage com tool_calls.

3.3 · O grafo

25:05–27:09 · Trecho do professor conferido no vídeo (aprox. 26:55)
react_builder = StateGraph(ReActState)
react_builder.add_node("model", model_node)
react_builder.add_node("tools", ToolNode(tools))

react_builder.add_edge(START, "model")
react_builder.add_conditional_edges("model", tools_condition)
react_builder.add_edge("tools", "model")

react_graph = react_builder.compile()

display(Image(react_graph.get_graph().draw_mermaid_png()))

São dois nós: "model" (raciocínio) e "tools" (o ToolNode com as duas ferramentas). add_conditional_edges("model", tools_condition) faz a escolha entre ferramentas e fim. A aresta tools → model é fixa: toda vez que uma ferramenta roda, o resultado volta para o modelo pensar de novo.

Como percorrer: a pergunta entra em model. Se o modelo pedir ferramenta, o fluxo vai para tools, que executa e volta para model. Esse laço se repete até o modelo responder em texto, sem tool_calls. Aí o fluxo vai para __end__.

4. Executando: o 30º presidente dos EUA

Vídeo · 27:19–36:30

A pergunta vem do livro: quantos anos tinha o 30º presidente dos Estados Unidos quando morreu? O professor explica por que ela é boa para testar: mistura um número de ordem (30º) com uma idade, o que pode confundir o modelo e revelar alucinação. Modelos atuais raramente caem nisso, mas vale testar.

29:33–30:36 · Trecho do professor (primeira execução, em inglês)
user_input = {
    "messages": [
        HumanMessage(
            content="How old was the 30th president of the United States when he died? "
                    "First search for his birth and death years, then use the calculator tool to compute the difference."
        )
    ]
}

for step_idx, chunk in enumerate(react_graph.stream(user_input), 1):
    node_name = list(chunk.keys())[0]
    node_output = chunk[node_name]
    last_msg = node_output["messages"][-1]

    print(f"=== Passo {step_idx} | Nó Executado: [{node_name}] ===")
    if hasattr(last_msg, "tool_calls") and last_msg.tool_calls:
        for tc in last_msg.tool_calls:
            print(f"  -> Decisão do LLM (Tool Call): {tc['name']}({tc['args']}) [id: {tc['id']}]")
    elif last_msg.type == "tool":
        print(f"  -> Retorno da Ferramenta [{last_msg.name}]: {str(last_msg.content)[:300]}...")
    else:
        print(f"  -> Resposta Final do Agente:\n{last_msg.content}")
    print()

stream devolve um chunk por nó executado. A chave do chunk é o nome do nó. O laço pega a última mensagem e mostra uma de três coisas: a decisão de chamar ferramenta (tool_calls), o retorno da ferramenta (type == "tool") ou a resposta final.

Repare na alternância model → tools → model → tools → model. O professor destaca a vantagem: em vez de escrever cadeias exatas de código, você cria nós condicionais e uma caixa de ferramentas, e o modelo toma as decisões úteis até chegar ao fim.

Pergunta do Pedro (35:40): dá para limitar o agente a, por exemplo, três buscas? Sim. Dá para fazer via prompt ou na definição da ferramenta, mas há formas mais elegantes que serão vistas adiante. Um exemplo já aparece nesta aula: o max_iterations do Reflection (seção 8).

O ponto para analisar nos seus agentes: o laço ReAct permite que o modelo veja o resultado errado e corrija a rota.

LangChain puro ou LangGraph?

Respondendo ao Eduardo, o professor reforça: quase tudo isto dá para fazer em LangChain puro, com mais restrições e mais trabalho. Para um agente que executa uma série bem definida de tarefas, use LangChain puro. O LangGraph vale quando você quer expandir para múltiplos agentes, modularizar blocos para crescer e auditar a execução nó a nó. Aplicar uma solução robusta demais a um problema simples é desperdício.

6. First Model: fixar a primeira ferramenta

Vídeo · 40:30–53:30

No ReAct padrão, toda interação começa no modelo, porque ele é o "cérebro" que escolhe a ferramenta. Mas em alguns sistemas a primeira etapa é sempre a mesma, como uma busca obrigatória. Deixar o modelo pensar nisso, mesmo que ele acerte, custa:

  • Latência e tokens: toda chamada de LLM custa, mesmo quando só serve para gerar o JSON da busca.
  • Confiabilidade: fixar a etapa elimina o risco de alucinação nessa decisão.

6.1 · A injeção sintética da ToolCall

O ToolNode espera encontrar no estado uma AIMessage com tool_calls. Então o professor cria um nó Python, first_model, que não chama LLM nenhuma: pega a pergunta do usuário e monta essa mensagem na mão.

43:20–44:22 · Trecho do notebook do professor; docstring e comentário omitidos
from uuid import uuid4
from langchain_core.messages import AIMessage, ToolCall

def first_model(state: ReActState) -> dict:
    user_query = state["messages"][-1].content

    forced_search_call = ToolCall(
        name=search.name,
        args={"query": user_query},
        id=uuid4().hex,
    )

    return {
        "messages": [
            AIMessage(content="", tool_calls=[forced_search_call])
        ]
    }

state["messages"][-1].content é a última mensagem (a pergunta). ToolCall recebe o nome oficial da ferramenta (search.name, que é wikipedia), os argumentos e um id único gerado por uuid4().hex. O nó retorna uma AIMessage vazia de texto, só com essa chamada. O professor ressalta que isso não é gambiarra: é um padrão aceito, melhor do que reestruturar todo o código.

Atenção ao comentário do código: o professor avisa (43:06 e 44:04) que o comentário original citava duckduckgo_search, mas a ferramenta agora é a Wikipedia. Por isso o comentário foi omitido aqui.

6.2 · O grafo com a primeira ferramenta fixa

44:56–46:15 · Trecho do professor conferido no vídeo (aprox. 46:05)

Como percorrer: __start__ → first_model → tools é um caminho fixo, sem LLM. Depois da primeira ferramenta, o fluxo entra no laço ReAct normal: tools → model, e model decide entre chamar mais ferramentas ou terminar.

Ou seja, fixar a etapa só ajuda de verdade quando a entrada já serve como parâmetro da ferramenta. O professor não comentou esse detalhe na aula; ele aparece no log.

6.4 · Quando usar

Exemplo do professor: o usuário digita o nome de um cliente e você vai buscá-lo no CRM. Não faz sentido o modelo ler o nome para decidir o que buscar. Essa etapa pode ser determinística, e o agente segue com o que ela extraiu.

Sua pergunta (50:48): o First Model é um "etiquetamento" determinístico para direcionar a LLM? Resposta do professor: é por aí. A ação precisa ser executada sempre, mas você não precisa de uma LLM para decidir como usar a ferramenta. Quando dá para transformar a entrada em saída sem invocar o modelo, faça isso. Usar o modelo até quando ele não precisa decidir é desperdício, e evitar isso mostra profissionalismo na arquitetura.

7. Tool Retrieval: escolher ferramentas por busca semântica

Vídeo · 53:33–1:08:44

7.1 · O problema: muitas ferramentas

Quando um agente cresce para 15, 30 ou 100 ferramentas (ERP, CRM, RH, financeiro, SQL, busca web), mandar todas no bind_tools causa três problemas:

  1. Queda na acurácia de seleção: o modelo confunde ferramentas com descrições parecidas, escolhe a errada ou alucina argumentos.
  2. Inflação de tokens: cada ferramenta ligada injeta seu JSON Schema completo no prompt oculto, em todas as chamadas.
  3. Mais latência: prompts maiores demoram mais para processar.

Parêntese do professor (55:16): ter muitas ferramentas em um único agente já é sinal de que talvez seja hora de dividir o sistema em vários agentes especializados. Nenhum agente precisa ser um Leonardo da Vinci que faz tudo. Esse é o assunto das próximas aulas.

7.2 · A solução: RAG sobre o catálogo de ferramentas

É a mesma ideia do RAG que você já viu, mas no lugar de documentos de regras entram as descrições das ferramentas. Antes do laço ReAct, um nó select_tools faz uma busca semântica e grava só as ferramentas mais relevantes no estado. O nó do modelo então faz o bind_tools só com elas.

1:01:20–1:02:08 · Recorte do catálogo do professor: 2 das 6 ferramentas novas; as outras 4 seguem o mesmo formato
@tool
def get_stock_price(ticker: str) -> str:
    """Consulta a cotação atual de uma ação na bolsa de valores (ex: PETR4, AAPL, MSFT)."""
    prices = {"PETR4": "R$ 38.45", "AAPL": "US$ 228.10", "MSFT": "US$ 445.00"}
    return prices.get(ticker.upper(), "Ticker não encontrado na base de cotações.")

@tool
def convert_currency(amount: float, from_currency: str, to_currency: str) -> str:
    """Converte valores monetários entre moedas internacionais (USD, BRL, EUR) usando a taxa de câmbio comercial."""
    rates_to_brl = {"USD": 5.80, "EUR": 6.15, "BRL": 1.0}
    in_brl = amount * rates_to_brl.get(from_currency.upper(), 1.0)
    converted = in_brl / rates_to_brl.get(to_currency.upper(), 1.0)
    return f"{amount} {from_currency.upper()} equivale a {converted:.2f} {to_currency.upper()}"

# ... mais 4 ferramentas no mesmo formato (RH, TI, estoque, frete)

enterprise_tools = [
    search,
    calculator,
    get_stock_price,
    convert_currency,

As ferramentas são simuladas: cotações e câmbio estão fixos em dicionários (por exemplo, AAPL = US$ 228,10 e USD = 5,80). O catálogo final tem 8 ferramentas: as 2 do começo e 6 corporativas (cotação, câmbio, férias no RH, chamado de TI, estoque e frete).

Aprox. 1:01:26 · Trecho do notebook do professor (indexação)
embeddings = OpenAIEmbeddings(model="text-embedding-3-small")
tool_documents = [
    Document(page_content=t.description, metadata={"name": t.name})
    for t in enterprise_tools
]

tools_vector_store = InMemoryVectorStore.from_documents(tool_documents, embeddings)
# Configuramos k=2 para enviar apenas as 2 ferramentas mais aderentes ao LLM
tools_retriever = tools_vector_store.as_retriever(search_kwargs={"k": 2})

Cada ferramenta vira um Document: o conteúdo é a descrição (t.description) e o nome vai em metadata. InMemoryVectorStore guarda os vetores na memória. as_retriever(search_kwargs={"k": 2}) devolve as 2 descrições mais parecidas com a pergunta.

1:02:16–1:04:07 · Trecho do notebook do professor; docstrings omitidas
class ToolRetrievalState(TypedDict):
    messages: Annotated[list[BaseMessage], add_messages]
    selected_tools: list[str]

base_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.1)

def select_tools(state: ToolRetrievalState) -> dict:
    user_query = state["messages"][-1].content
    matched_docs = tools_retriever.invoke(user_query)
    selected_names = [doc.metadata["name"] for doc in matched_docs]
    return {"selected_tools": selected_names}

def dynamic_model_node(state: ToolRetrievalState) -> dict:
    filtered_tools = [
        t for t in enterprise_tools if t.name in state["selected_tools"]
    ]
    res = base_llm.bind_tools(filtered_tools).invoke(state["messages"])
    return {"messages": [res]}

O estado ganha o campo selected_tools. select_tools busca no retriever com a pergunta e devolve só os nomes. dynamic_model_node filtra a lista completa pelos nomes selecionados e faz o bind_tools a cada chamada. O professor reforça: todos os nós recebem o estado como parâmetro, e é dele que tiram tudo o que precisam.

8. Reflection: gerar, criticar e refinar

Vídeo · 1:08:44–1:25:28

O Reflection estende o ReAct com um ciclo explícito de avaliação e autocrítica. Pedir um texto técnico, um código ou um relatório em uma única passada costuma dar um resultado genérico. Aqui o trabalho é dividido em três nós:

NóPapel
generate (autor)Escreve o primeiro rascunho ou reescreve o anterior incorporando a crítica.
reflect (crítico)Avalia o rascunho por critérios definidos e dá nota, lacunas e veredito.

class ReflectionCritique(BaseModel):
    """Avaliação estruturada de qualidade do rascunho gerado."""
    clarity_and_depth_score: int = Field(
        description="Nota de 1 a 10 avaliando precisão técnica, clareza e profundidade do texto."
    )
    missing_elements: list[str] = Field(
        description="Lista de conceitos técnicos, exemplos concretos ou métricas que faltaram no rascunho."
    )
    actionable_feedback: str = Field(
        description="Instruções diretas e específicas do que o autor deve reescrever ou adicionar na próxima versão."
    )
    is_approved: bool = Field(
        description="True apenas se a nota for >= 9 e não houver lacunas importantes; False caso precise de nova revisão."
    )

class ReflexionState(TypedDict):
    topic: str
    current_draft: str
    reflection_feedback: str
    score: int
    is_approved: bool
    iteration: int
    max_iterations: int
    final_content: str
    history_log: Annotated[list[str], operator.add]

author_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.5)
critic_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0.1).with_structured_output(ReflectionCritique)

ReflectionCritique é um BaseModel do Pydantic, como nas aulas de LangChain: cada campo tem uma description que orienta o modelo. O estado guarda tópico, rascunho, feedback, nota, aprovação, contador de iterações, limite, conteúdo final e um log. O history_log usa operator.add como reducer, então cada nó só acrescenta linhas.

São duas LLMs: o autor com temperatura 0.5 (um pouco maior, para não repetir sempre a mesma resposta) e o crítico com temperatura 0.1 e with_structured_output, que devolve um objeto ReflectionCritique em vez de texto. O max_iterations é uma forma simples e comum de limitar o laço (respondendo à pergunta do Pedro).

Pergunta do Eduardo (1:18:39): o crítico poderia ser outra LLM, talvez mais capaz? Sim, e esse é o padrão ouro da indústria: escolher o modelo conforme a demanda de cada etapa.

def generate_node(state: ReflexionState) -> dict:
    iteration = state.get("iteration", 0) + 1

    if iteration == 1:
        # Primeira iteração: solicitamos um rascunho inicial curto para vermos a evolução
        prompt = [
            SystemMessage(
                content="Você é um redator técnico. Escreva uma primeira versão curta (1 parágrafo simples) "
                        "sobre o tópico solicitado, sem entrar ainda em detalhes profundos de arquitetura."
            ),
            HumanMessage(content=f"Tópico: {state['topic']}")
        ]
    else:
        # Iterações subsequentes: incorpora o feedback rigoroso do nó 'reflect'
        prompt = [
            SystemMessage(
                content="Você é um autor sênior de engenharia de IA. Reescreva e expanda o rascunho anterior "
                        "incorporando integralmente todas as críticas e elementos faltantes apontados pelo revisor."
            ),
            HumanMessage(
                content=f"Tópico Original: {state['topic']}\n\n"
                        f"Rascunho Anterior:\n{state['current_draft']}\n\n"
                        f"Crítica do Revisor:\n{state['reflection_feedback']}"
            )
        ]

    response = author_llm.invoke(prompt)
    log_entry = f"[Iteração {iteration} - Generate] Rascunho produzido ({len(response.content)} caracteres)."

    return {

        "iteration": iteration,
        "history_log": [log_entry],
    }

Na iteração 1, o prompt pede de propósito um texto curto e raso, para dar para ver a evolução. Nas seguintes, o prompt muda para "autor sênior" e inclui o tópico, o rascunho anterior e a crítica. Tudo isso só está disponível porque esses campos foram definidos no estado. O nó devolve o rascunho, o número da iteração e uma linha de log.

def reflect_node(state: ReflexionState) -> dict:
    prompt = [
        SystemMessage(
            content="Você é um editor técnico rigoroso de um livro de Arquitetura de Agentes. "
                    "Avalie o rascunho. Para ser aprovado (nota >= 9), o texto DEVE conter: "
                    "(1) explicação clara do conceito, (2) um exemplo concreto de caso de uso em produção "
                    "e (3) análise explícita de trade-offs de latência vs. confiabilidade. "
                    "Se faltar qualquer um desses itens, reprove (is_approved=False) e exija a correção."
        ),
        HumanMessage(content=f"Tópico: {state['topic']}\n\nRascunho Atual:\n{state['current_draft']}")
    ]

    critique: ReflectionCritique = critic_llm.invoke(prompt)
    formatted_feedback = (
        f"Nota: {critique.clarity_and_depth_score}/10 | Aprovado: {critique.is_approved}\n"
        f"Lacunas: {', '.join(critique.missing_elements)}\n"
        f"Direcionamento: {critique.actionable_feedback}"
    )
    log_entry = f"[Iteração {state['iteration']} - Reflect] Nota: {critique.clarity_and_depth_score}/10 (Aprovado={critique.is_approved})"

    return {
        "reflection_feedback": formatted_feedback,
        "score": critique.clarity_and_depth_score,
        "is_approved": critique.is_approved,
        "history_log": [log_entry],
    }

O prompt define o que é aprovação: nota ≥ 9 e três itens obrigatórios (conceito claro, exemplo concreto em produção e análise de trade-offs de latência vs. confiabilidade). O resultado critique já é um objeto com campos. O nó monta um feedback em texto e grava nota e aprovação no estado. O professor compara o is_approved a um interruptor no "cérebro" do grafo.

def finalize_node(state: ReflexionState) -> dict:
    header = (
        f"# Documento Finalizado (Iterações: {state['iteration']} | Nota Final: {state['score']}/10)\n\n"
    )
    return {
        "final_content": header + state["current_draft"],
        "history_log": ["[Finalize] Conteúdo consolidado e entregue."],
    }

def should_continue(state: ReflexionState) -> Literal["generate", "finalize"]:
    if state["is_approved"] or state["iteration"] >= state["max_iterations"]:
        return "finalize"
    return "generate"

should_continue é a função da aresta condicional, um padrão muito comum em projetos LangGraph. Ela manda para "finalize" se o texto foi aprovado ou se o limite de iterações chegou. Caso contrário, volta para "generate". O tipo Literal["generate", "finalize"] deixa claro quais destinos existem.

10. Plan-and-Execute: planejar antes de agir

Vídeo · 1:27:57–1:44:21

10.1 · Os limites do ReAct em tarefas longas

O ReAct planeja só um passo à frente em cada iteração (raciocínio "míope"). Em tarefas com 5 ou 10 etapas dependentes, isso causa:

  1. Custo e latência: cada chamada simples de ferramenta invoca a LLM principal com todo o histórico.
  2. Desvio de objetivo: com resultados longos no meio do caminho, o agente perde de vista o pedido original.
  3. Falta de visão global: o agente não confere se mapeou todos os subproblemas antes de sair executando.

10.2 · Três componentes

Inspirada no paper Plan-and-Solve Prompting (Wang e outros) e em arquiteturas clássicas de robótica, a arquitetura separa estratégia de execução:

ComponenteO que faz
plannerRecebe o objetivo e gera um plano com várias etapas.
executorPega só a primeira etapa pendente e a executa com as ferramentas.
replannerCompara o que foi feito com o objetivo. Se terminou, escreve a resposta final. Se não, atualiza as etapas que faltam.

10.3 · Contratos, estado e modelos

1:31:31–1:33:15 · Trecho do notebook do professor; comentários de numeração omitidos
class PlanSchema(BaseModel):
    """Plano ordenado de etapas para resolver o objetivo do usuário."""
    steps: list[str] = Field(
        description="Lista sequencial de etapas claras e atômicas. Cada etapa deve ser uma ação verificável."
    )

class ReplanDecision(BaseModel):
    """Decisão do Monitor/Replanner após inspecionar o progresso das etapas executadas."""
    is_complete: bool = Field(
        description="True se todas as informações necessárias para responder ao objetivo original já foram obtidas em past_steps; False caso ainda existam etapas pendentes."
    )
    updated_remaining_steps: list[str] = Field(
        description="Se is_complete=False, lista atualizada apenas com as etapas que AINDA faltam ser executadas. Se is_complete=True, retorne lista vazia []."
    )
    final_response: Optional[str] = Field(
        default=None,
        description="Se is_complete=True, redija aqui a resposta final completa e consolidada para o usuário com todos os números calculados."
    )

class PlanExecuteState(TypedDict):
    objective: str
    plan: list[str]
    past_steps: Annotated[list[tuple[str, str]], operator.add]
    final_response: str

planner_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0).with_structured_output(PlanSchema)
replanner_llm = ChatOpenAI(model="gpt-4o-mini", temperature=0).with_structured_output(ReplanDecision)

Os dois schemas Pydantic são contratos determinísticos: o planner sempre devolve uma lista steps e o replanner sempre devolve is_complete, updated_remaining_steps e, se terminou, final_response. O estado guarda o objetivo, o plano (o que falta), os passos já feitos e a resposta final. past_steps usa operator.add, então cada execução só acrescenta a tupla (etapa, resultado).

Os dois usam o mesmo modelo, mas o professor reforça: vale adaptar o modelo a cada função, consultando benchmarks e a opinião da comunidade.

def planner_node(state: PlanExecuteState) -> dict:
    sys_prompt = (
        "Você é um planejador estratégico corporativo. Dado um objetivo complexo do usuário, "
        "decomponha-o em uma lista enxuta de etapas sequenciais (3 a 4 etapas). "
        "Não adicione etapas supérfluas; cada etapa será executada por um agente com acesso a ferramentas "
        "de cotação de ações, câmbio de moedas, estoque de galpão, cálculo de frete e calculadora."
    )
    plan_result: PlanSchema = planner_llm.invoke([
        SystemMessage(content=sys_prompt),
        HumanMessage(content=f"Objetivo: {state['objective']}")
    ])
    return {"plan": plan_result.steps}

def executor_node(state: PlanExecuteState) -> dict:
    current_step = state["plan"][0]
    past_context = "\n".join([f"- Etapa concluída: {s} => Resultado: {r}" for s, r in state.get("past_steps", [])])

    execution_prompt = (
        f"Objetivo Global: {state['objective']}\n"
        f"Contexto de Etapas Anteriores:\n{past_context if past_context else 'Nenhuma etapa executada ainda.'}\n\n"
        f"SUA TAREFA ATUAL: Execute APENAS a seguinte etapa e retorne o resultado exato obtido: '{current_step}'"
    )

    agent_res = task_executor_agent.invoke({"messages": [HumanMessage(content=execution_prompt)]})
    step_output = agent_res["messages"][-1].content

    return {
        "past_steps": [(current_step, step_output)]
    }

planner_node pede de 3 a 4 etapas, sem etapas supérfluas, e recebe um PlanSchema. executor_node pega state["plan"][0], monta um prompt com o objetivo global e o que já foi feito, e chama o subgrafo. O resultado da etapa é a última mensagem do subgrafo, guardada em past_steps.

1:37:32–1:38:38 · Trecho do notebook do professor; docstrings omitidas
def replanner_node(state: PlanExecuteState) -> dict:
    past_formatted = "\n".join([f"- {s}: {r}" for s, r in state["past_steps"]])
    remaining_if_not_updated = state["plan"][1:]

    replan_prompt = (
        f"Objetivo Original do Usuário:\n{state['objective']}\n\n"
        f"Plano Original:\n{state['plan']}\n\n"
        f"Etapas Já Executadas e Seus Resultados (past_steps):\n{past_formatted}\n\n"
        f"Etapas que restavam na fila:\n{remaining_if_not_updated}\n\n"
        "Avalie: se todas as informações pedidas no Objetivo Original já constam nos resultados acima, "
        "marque is_complete=True e escreva a final_response detalhada. "
        "Caso contrário, marque is_complete=False e forneça updated_remaining_steps apenas com o que ainda falta fazer."
    )

    decision: ReplanDecision = replanner_llm.invoke([
        SystemMessage(content="Você é o Monitor/Replanner de uma arquitetura Plan-and-Execute."),
        HumanMessage(content=replan_prompt)
    ])

    if decision.is_complete:
        return {"final_response": decision.final_response, "plan": []}
    else:
        return {"plan": decision.updated_remaining_steps}

def should_continue_plan(state: PlanExecuteState) -> Literal["executor", "__end__"]:
    if state.get("final_response") or not state.get("plan"):
        return "__end__"
    return "executor"

O replanner recebe o objetivo original, o plano, as etapas feitas e as que restavam. Se tudo o que foi pedido já está nos resultados, ele devolve a final_response e esvazia o plano. Senão, devolve só as etapas que faltam. should_continue_plan encerra ("__end__") quando há resposta final ou o plano ficou vazio; senão volta ao executor.

O que preciso lembrar

Vídeo · Revisão da aula

  • Agente autônomo = decide, tem opções e age no ambiente, num laço que a própria LLM controla.
  • bind_tools liga os schemas; o modelo devolve tool_calls; o ToolNode executa; tools_condition decide entre tools e END.
  • No ReAct, a aresta tools → model é fixa: todo resultado volta para o modelo pensar.
  • Se uma etapa é sempre igual, fixe-a sem LLM (First Model). Usar LLM sem necessidade é desperdício.
  • Muitas ferramentas: busque as top-k por descrição (Tool Retrieval) ou pense em dividir em vários agentes.
  • Reflection = autor + crítico com saída estruturada + limite de iterações.
  • Plan-and-Execute guarda objetivo e plano no estado; o replanner evita o desvio de objetivo.
  • Tudo nesta aula ainda é um único agente. Para tarefas simples e bem definidas, LangChain puro continua valendo.
